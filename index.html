Two parallel challenges: (1) use the Linux command line to find specific IP addresses in remote server logs and isolate HTTP 400/500 errors into structured files; (2) query a PostgreSQL database of Chicago taxi trips to answer real business questions about fleet size, company distribution, weather impact, and trip volume.

⚙️ What I Did

Console (Linux/Bash): Navigated a remote server and used grep -R with a regex anchor (^233.201) to filter logs by IP prefix across multiple directories. Created a bug1/events/ directory structure, extracted the target date's log file as main.txt, and separated HTTP errors into dedicated files:

  • grep '\" 400' main.txt > 400.txt — isolated all client error entries
  • grep '\" 500' main.txt > 500.txt — isolated all server error entries

SQL (PostgreSQL — Chicago Taxi DB): Wrote 4 queries across 4 related tables (cabs, trips, weather_records, neighborhoods):

  • Fleet count: COUNT(DISTINCT vehicle_id) → 5,529 unique vehicles (vs. 10,550 planned — shortage confirmed)
  • Company distribution: GROUP BY + HAVING COUNT(*) < 100 ORDER BY cnt DESC → 51 companies with under 100 cabs
  • Weather classification: CASE WHEN description ILIKE '%rain%' OR '%storm%' → labeled each hour Good/Bad for a 24-hour window
  • Trip volume by company: INNER JOIN cabs + trips + COUNT(trip_id) → trip totals for Nov 15–16, 2017, ranked by activity
✅ Learning

Discovered that the [45]00 regex pattern is more efficient than two separate greps when filtering by HTTP error family — a key pattern for log analysis at scale. In SQL, internalized the difference between WHERE (filters rows before grouping) and HAVING (filters after aggregation), and learned to join trips with weather_records via matching timestamps since there is no direct foreign key between them.

Project 06
🚗 Urban Routes — UI Automation
End-to-End Web Testing · Selenium · Page Object Model · TripleTen Bootcamp, Sprint 9 (2026)
E2E Automation
🎯 Problem

Automate the complete taxi-ordering happy path on the Urban Routes web app using Selenium WebDriver and the Page Object Model (POM) pattern. The suite must cover 11 scenarios — from setting the route to verifying the driver-arrival modal — while handling real-world browser challenges: hidden elements, dynamic buttons, network-intercepted SMS codes, and long async waits.

📊 Results & Impact

⚙️ What I Did

Built a structured Selenium/Pytest framework following the Page Object Model pattern, with 4 modules and a clear separation of concerns:

  • data/data.py — all test data (URL, addresses, phone, card, message)
  • pages/urban_routes_page.py — 30+ locators (By.ID, CSS, XPath) and page-action methods; hidden elements use presence_of_element_located, visible ones use visibility_of_element_located
  • helpers/retrieve_code.py — intercepts the SMS confirmation code from Chrome's performance network logs (goog:loggingPrefs)
  • tests/test_urban_routes.py — 11 ordered tests with setup_class / teardown_class for browser lifecycle

Key technical challenges solved:

  • CVV field blur: simulated TAB keypress (Keys.TAB) after entering the code to trigger the blur event and enable the "Agregar" button
  • SMS code retrieval from browser network logs instead of a real SMS service
  • Driver-arrival modal: used a 60-second explicit wait separate from the default 5s wait
  • Ice cream counter max: verified that 'disabled' appears in the "+" button class attribute after reaching the limit
✅ Learning

The Page Object Model transforms tests from fragile script sequences into maintainable, readable workflows — if a locator changes, only the Page Object needs updating, not every test. Hidden/disabled elements require presence_of_element_located instead of visibility-based waits; using the wrong one causes flaky failures. Intercepting SMS codes from Chrome's performance logs is a real-world automation technique that avoids dependency on external services during testing.
